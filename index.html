SYNCHRONOUS
REST · gRPC · GraphQL · WebSocket — caller blocks until response
Key Characteristic
Caller sends request and WAITS for response before continuing. Creates temporal coupling — if downstream is unavailable, upstream fails. Best when you need immediate data or user is waiting for a reply.

🌐
REST over HTTP/1.1 & HTTP/2
Representational State Transfer
+
How it works: Resources are represented as URLs. HTTP verbs (GET, POST, PUT, DELETE, PATCH) define operations. Responses in JSON or XML. Stateless — each request is self-contained.

HTTP Methods:
GET /orders/123 — Read a resource
POST /orders — Create new
PUT /orders/123 — Replace
PATCH /orders/123 — Partial update
DELETE /orders/123 — Remove

Status Codes to know:
200 OK · 201 Created · 204 No Content
301 Moved · 304 Not Modified
400 Bad Request · 401 Unauthorized · 403 Forbidden · 404 Not Found · 409 Conflict · 429 Too Many Requests
500 Internal Error · 502 Bad Gateway · 503 Service Unavailable

Pros: Human-readable, universal tooling, easy debugging, browser-native
Cons: Verbose (JSON overhead), text-based, no schema enforcement, HTTP/1.1 head-of-line blocking
// REST Request POST /api/v1/orders HTTP/1.1 Host: order-service Content-Type: application/json Authorization: Bearer {token} { "customerId": "abc-123", "items": [{ "sku": "PROD-001", "qty": 2 }] }
⚡
gRPC over HTTP/2
Google Remote Procedure Call
+
How it works: Define service contracts in .proto files. Code-generate client/server stubs. Binary Protocol Buffers serialization over multiplexed HTTP/2 streams.

4 Communication Modes:
Unary — 1 req → 1 res (like REST)
Server Streaming — 1 req → stream of res
Client Streaming — stream of req → 1 res
Bidirectional — stream ↔ stream

Why faster than REST:
• Binary Protobuf vs text JSON (~5-10× smaller)
• HTTP/2 multiplexing, no HOL blocking
• Header compression (HPACK)
• Connection reuse

Pros: Speed, strict contracts, streaming, auto-generated clients, strong typing
Cons: Not browser-native, binary = harder to debug, requires proto schema sharing
// order.proto syntax = "proto3"; service OrderService { rpc CreateOrder (OrderRequest) returns (OrderResponse); rpc StreamOrders (Filter) returns (stream Order); } message OrderRequest { string customer_id = 1; repeated Item items = 2; }
REST vs gRPC — Performance Comparison
Throughput (RPS)REST: 12k · gRPC: 50k
Payload SizeREST (JSON): 100% · gRPC (Proto): ~20%
Developer ExperienceREST: Easy · gRPC: Moderate
Synchronous
🔮 GraphQL
Query language for APIs. Client specifies exact fields needed — no over-fetching or under-fetching. Single endpoint (/graphql). Schema-first with types, queries, mutations, subscriptions.

Best for: API gateway aggregation (BFF pattern), mobile clients with bandwidth constraints, complex data graphs.

Avoid when: Simple CRUD — GraphQL adds significant complexity for minimal gain. N+1 query problem requires DataLoader.
Real-time
🔌 WebSocket
Full-duplex TCP connection over HTTP upgrade. Once handshake is done, both parties can push messages anytime. Low latency (no HTTP overhead per message).

Best for: Chat, live dashboards, collaborative editing, gaming, stock tickers, notifications.

Variants: Socket.IO (reconnect/rooms), Server-Sent Events (SSE) for server→client only pushes.
03
ASYNCHRONOUS
Message Queues · Event Streaming · Pub/Sub — fire and forget
Key Characteristic
Producer sends message and continues immediately. Consumer processes whenever ready. Temporal decoupling — both services don't need to be available simultaneously. Enables higher throughput, resilience, and scalability at the cost of eventual consistency.
🌊
Apache Kafka
Distributed Event Streaming Platform
+
Core Concepts:
Topic — named channel for events
Partition — ordered, immutable log within topic
Offset — position within partition log
Producer — writes events to topics
Consumer Group — reads and processes events
Broker — Kafka server instance
ZooKeeper/KRaft — cluster coordination

Key properties:
• Messages retained on disk (configurable TTL)
• Consumers can replay from any offset
• Horizontal scale via partition count
• At-least-once delivery by default
• Exactly-once with idempotent producers + transactions
• Up to millions of events/second

Best for: Event sourcing, CQRS, audit logs, stream processing, data pipelines
Avoid when: Simple task queues, low volume, or when replay isn't needed
// Kafka Producer (Node.js) const producer = kafka.producer({ idempotent: true }) await producer.send({ topic: 'order-events', messages: [{ key: order.id, value: JSON.stringify({ type: 'ORDER_PLACED', ...order }), headers: { 'correlation-id': requestId } }] })
🐇
RabbitMQ
AMQP-based Message Broker
+
Core Concepts:
Exchange — receives messages, routes to queues
Queue — buffer holding messages
Binding — routing rule (exchange→queue)
Routing Key — criteria for routing decisions
Consumer — reads from queue, acks/nacks
DLX — Dead Letter Exchange for failed msgs

Exchange Types:
Direct — routes by exact routing key match
Fanout — broadcasts to ALL bound queues
Topic — pattern matching (order.*.created)
Headers — matches on message headers

Message lifecycle:
Producer → Exchange → Queue → Consumer → ACK/NACK
NACK → DLQ (Dead Letter Queue) → alerting

Best for: Task queues, flexible routing, low-latency delivery, work distribution
Avoid when: Need message replay, high-throughput streaming
// RabbitMQ Consumer (Python) def process_order(ch, method, props, body): order = json.loads(body) try: handle_order(order) ch.basic_ack(method.delivery_tag) except Exception: ch.basic_nack(method.delivery_tag, requeue=False) # → DLQ

Pattern
📢 Pub / Sub
One producer → Many consumers. Each consumer gets its own copy independently. Decoupled — producer doesn't know consumers exist.

Example: OrderPlaced event → Inventory, Billing, Notification, Analytics all consume independently.
Pattern
📬 Point-to-Point
Message delivered to exactly ONE consumer from a group. Load-balanced across instances. After consumption, message is gone.

Example: Image resize job queue — worker pool picks up jobs one at a time. Each job processed exactly once.
Pattern
↩️ Request-Reply
Simulates sync behavior over async infrastructure. Include replyTo queue + correlationId in message header. Producer subscribes to reply queue and waits.

Use when: Need async infrastructure benefits but require a response (e.g., price calculation).
04
DESIGN PATTERNS
Outbox · CQRS · Event Sourcing · Competing Consumers · Priority Queue
📤
Transactional Outbox Pattern
Dual-write consistency guarantee
+
Problem: How do you atomically update DB and publish a message? A service crash between the two operations causes inconsistency.

Solution:
1. Write DB update + event to OUTBOX table in same transaction
2. Message relay (CDC/poller) reads outbox and publishes to broker
3. Mark outbox record as sent

Relay options:
• Polling — simple, adds DB load
• Debezium CDC — stream from binlog, zero-delay

Guarantees: Exactly-once DB write. At-least-once message publish (idempotent consumer needed)
// Atomic: order + outbox in one tx BEGIN TRANSACTION; INSERT INTO orders VALUES (...); INSERT INTO outbox (event_type, payload) VALUES ('ORDER_CREATED', '{...}'); COMMIT;
⚡
CQRS Pattern
Command Query Responsibility Segregation
+
Problem: Read and write workloads have different scaling needs. Complex reports slow down write operations.

Solution: Separate write model (Commands) from read model (Queries). Events synchronize the read side.

Write side: Validates + processes commands → emits events
Read side: Subscribes to events → builds optimized read models (denormalized, indexed)

Trade-off: Eventual consistency between write and read sides (typically milliseconds).

Benefits: Scale reads/writes independently, tailored query models, simpler read queries
// Command handler handleCreateOrder(cmd) { order.validate(cmd) await orderRepo.save(order) await eventBus.publish('OrderCreated', order) } // Read model projector on('OrderCreated', (event) => { orderSummaryDb.upsert(event.data) })
📜
Event Sourcing
State as immutable event log
+
Core idea: Don't store current state — store ALL events that led to it. Reconstruct state by replaying events.

Event Store: Append-only log of domain events
Snapshots — periodic state captures for fast reconstruction

Benefits:
• Full audit history built-in
• Time-travel debugging
• Multiple read models from same events
• Natural fit with CQRS

Challenges:
• Schema evolution (event versioning)
• Eventual consistency
• Query complexity
• Upcasting old events
// Events in store: OrderCreated { id, items, at: T1 } ItemAdded { orderId, item, at: T2 } Discounted { orderId, pct: 10, at: T3 } OrderPlaced { orderId, at: T4 } // Reconstruct current state: state = events.reduce(apply, initialState)
👥
Competing Consumers
Horizontal scale of message processing
+
How it works: Multiple consumer instances subscribe to the same queue. Broker delivers each message to exactly one consumer. Natural load balancing.

Scaling: Add more consumer instances during peak. Remove during off-peak. Autoscale based on queue depth (KEDA, SQS → Lambda).

Considerations:
• Message ordering not guaranteed across consumers
• Idempotency required (duplicate delivery possible)
• Consumer groups in Kafka: each partition → 1 consumer

Best for: CPU-intensive jobs, background processing, image/video processing, report generation

SAGA PATTERN
Distributed transactions without 2PC — choreography vs orchestration
Why Not 2-Phase Commit (2PC)?
2PC requires all services to lock resources until all agree to commit. In microservices this causes tight coupling, single point of failure (coordinator), and massive latency. Sagas replace 2PC with a sequence of local transactions + compensating transactions for rollback.
Choreography — Event-Driven

PaymentProcessed ✓
Payment Svc
Inventory Svc

OrderConfirmed ✓
Shipping Svc
↳ Failure path — compensating transactions
Inventory Svc

Payment Svc
Pros: No central coordinator, loose coupling, simple for short sagas
Cons: Hard to trace/debug, implicit logic spread across services, risk of cyclic events
Orchestration — Central Coordinator
Step 1
Saga Orchestrator starts
Orchestrator receives CreateOrder command. Begins saga state machine. Records saga ID + current state.
Step 2
Command → Payment Service
Orchestrator sends ProcessPayment command. Awaits reply event. Transitions state on success/failure.
Step 3
Command → Inventory Service
Sends ReserveStock command after payment success. Inventory replies StockReserved or StockUnavailable.
Step 4a — Success
Order Confirmed
Orchestrator marks saga complete. Publishes OrderConfirmed event to notify downstream.
Step 4b — Failure
Compensate
Orchestrator sends RefundPayment + ReleaseStock commands. Marks saga as Failed + CompensationComplete.
Pros: Clear flow, easy to trace/debug, centralized failure handling
Cons: Orchestrator is a dependency, risk of god service, harder to add new participants

SERVICE DISCOVERY
Client-side · Server-side · DNS · Service Registry
Client-Side Discovery
🔍 Client Resolves
Client queries service registry (Consul, Eureka, etcd) to get list of available instances. Client applies load balancing algorithm (round-robin, least-connections, random) and connects directly.

Tools: Netflix Eureka, HashiCorp Consul, Apache Zookeeper

Pros: Client controls LB algorithm. No extra hop.
Cons: LB logic in every client, language-specific libraries needed.
// Client queries registry first instances = registry.getInstances('order-service') chosen = loadBalancer.choose(instances) result = await http.get(chosen.url + '/orders')
Server-Side Discovery
⚖️ Load Balancer Resolves
Client sends request to load balancer / router. LB queries registry and forwards to a healthy instance. Client is fully unaware of discovery.

Tools: AWS ALB, Kubernetes DNS/Services, NGINX, HAProxy, Envoy

Pros: Client is simple. Language-agnostic. Consistent LB behavior.
Cons: Extra network hop. LB is a potential bottleneck and SPOF without HA setup.
# Kubernetes DNS resolves automatically # http://order-service → Service → Pod IPs result = requests.get( 'http://order-service.default.svc.cluster.local/orders' )
DNS-Based
🌐 DNS Discovery
Service name resolves via DNS to IP(s). Kubernetes uses CoreDNS. Simple but DNS caching can cause stale IPs. SRV records include port info.

TTL must be low (1-5s) for fast failover. Not suitable for rapid instance churn.
Health Checks
💓 Health & Registration
Services register on startup with metadata (host, port, version, tags). Send periodic heartbeats. Registry deregisters on failed health check.

Health check types: HTTP, TCP, gRPC, script, TTL (service pings registry).
Kubernetes
☸️ K8s Native
Services exposed via ClusterIP, NodePort, or LoadBalancer. kube-proxy sets up iptables rules. CoreDNS provides service DNS. Endpoints object tracks healthy pods automatically.

RESILIENCE PATTERNS
Circuit Breaker · Retry · Timeout · Bulkhead · Rate Limit · Fallback · Backpressure
⚡ Circuit Breaker — State Machine
Tracks failure rate over a rolling time window. Trips open to stop all calls to a failing service, allowing it to recover. Periodically allows probe requests in half-open state.
🟢
CLOSED
Normal operation. All requests pass through. Failure counter increments on errors. Trips OPEN if threshold exceeded (e.g., >50% in 10s).
🔴
OPEN
All requests fail immediately (no network call). Returns cached value / error / fallback. After timeout (e.g., 30s) transitions to HALF-OPEN.
🟡
HALF-OPEN
Allows limited probe requests through. If probes succeed → CLOSED. If probes fail → OPEN again. Prevents premature re-engagement.
// Resilience4j Circuit Breaker (Java) CircuitBreaker cb = CircuitBreaker.ofDefaults("orderSvc"); var supplier = CircuitBreaker.decorateSupplier(cb, () -> orderService.getOrder(id) ); var result = Try.ofSupplier(supplier) .recover(ex -> fallback(id)) .get();
🔁
Retry + Exponential Backoff
+
Retry only transient failures: Network timeouts, 503 Service Unavailable, 429 Too Many Requests. Never retry on 400, 401, 403 (client errors).

Exponential Backoff: delay = baseDelay × 2^attempt
Attempt 1: 100ms, 2: 200ms, 3: 400ms, 4: 800ms...

Jitter: Add random offset to prevent thundering herd (all retries hitting at same time).
delay = random(0, baseDelay × 2^attempt)

Max retries: Always cap — 3-5 retries max. Combine with circuit breaker.
// With jitter function backoff(attempt, base = 100) { const exp = base * Math.pow(2, attempt) const jitter = Math.random() * exp return Math.min(exp + jitter, 30000) }
🪣
Bulkhead Pattern
+
Problem: A slow downstream service consumes all threads/connections, starving other services.

Bulkhead: Isolate resources per dependency. Each downstream gets its own thread pool / semaphore / connection pool. One slow service can't affect others.

Thread Pool Bulkhead: Fixed threads per service. Requests queue or fail when pool exhausted.
Semaphore Bulkhead: Limit concurrent calls per service. Simpler, same thread. Less isolation.
// Separate pools per downstream paymentPool = new ThreadPool({ size: 10 }) inventoryPool = new ThreadPool({ size: 5 }) // inventory slowdown can't starve payment
Resilience
⏱️ Timeout
Always set aggressive timeouts. A hanging call consuming a thread is worse than a fast failure. Use different timeouts per dependency based on SLA. Connection timeout ≠ read timeout.
Resilience
🏃 Fallback
Return cached data, default value, or degraded response when service fails. Must be intentionally designed. Stale cache better than error. Degrade gracefully — partial functionality beats full failure.
Resilience
🚦 Rate Limiting
Token Bucket — smooth bursts. Fixed Window — simple. Sliding Window — accurate. Leaky Bucket — strict rate. Apply at API gateway and per-client. Return 429 with Retry-After header.
Resilience
💨 Backpressure
Consumers signal producers to slow down when overwhelmed. Prevents OOM and cascade failures. Implemented via bounded queues, reactive streams (RxJava, Project Reactor), flow control in gRPC.

SERVICE MESH
Istio · Linkerd · Envoy — infrastructure-layer cross-cutting concerns
What is a Service Mesh?
A dedicated infrastructure layer that handles service-to-service communication via sidecar proxies deployed alongside each service. Offloads cross-cutting concerns (mTLS, retries, tracing, LB) from application code to the infrastructure — without any code changes.

When NOT to use a service mesh
Adds 10-30ms latency, significant CPU overhead, and operational complexity. Only justified with 20+ services where cross-cutting concerns are a pain. Start without it.

API GATEWAY & BFF
Single entry point · Request aggregation · Backend for Frontend pattern
Gateway
🚪 API Gateway Responsibilities
Auth Layer
JWT validation, OAuth2 token introspection, API key verification. Centralized — services trust gateway. No per-service auth code.
Rate Limiting
Per-client, per-endpoint, per-IP limits. Token bucket / sliding window. 429 with Retry-After. Protect backend services.
Request Routing
Path-based, header-based, version-based routing. /api/v1/orders → order-service. A/B routing by user segment.
Aggregation
Fan out to multiple services. Merge responses into single payload. Reduce client round-trips. Schema transformation.
SSL Termination
Handle TLS at edge. Internal services communicate over plain HTTP (or mesh-managed mTLS). Simplifies cert management.
BFF Pattern
🖥️ Backend for Frontend
One API gateway per client type. Each BFF tailors the API to its client's specific needs — shape, verbosity, auth model, and optimization.

SECURITY
Zero Trust · mTLS · JWT · OAuth2 · SPIFFE — auth between services
Zero Trust
🔐 Zero Trust Network
"Never trust, always verify." Every service-to-service call is authenticated and authorized — even internal calls. No implicit trust based on network location.

Assume breach. Minimize blast radius. Verify explicitly at every hop.
Service Auth
🤝 Mutual TLS (mTLS)
Both client and server present certificates. Bi-directional authentication — proves identity of caller AND callee. SPIFFE SVID certificates issued per workload. Service mesh automates this transparently.

Service A cert: spiffe://cluster.local/ns/default/sa/order-svc
User Auth
🎟️ JWT + OAuth2
Client authenticates at gateway → receives JWT. JWT propagated to downstream services. Services validate signature, check claims (sub, roles, exp). Short-lived tokens (15min) + refresh tokens.

OAuth2 flows: Client Credentials (M2M), Auth Code (user), Device Flow (IoT).
Secrets Management
🗝️ Secrets at Rest & Transit
Never hardcode secrets. Use secrets managers (HashiCorp Vault, AWS Secrets Manager, K8s Secrets with external-secrets-operator). Rotate credentials automatically. Audit access to secrets.

Principle: Services receive secrets via environment variables or file mounts, never from source code.
Message Security
📨 Securing Async Messages
Kafka: SASL authentication, TLS in transit, ACLs per topic. Message-level signing for integrity. Dead Letter Queues require same ACLs.

Avoid putting sensitive PII in messages. Use reference (customer ID) not full customer object. Consumers can fetch details if needed.

DECISION GUIDE
Choosing the right communication style for your use case
Does the caller need an immediate response to continue?
YES → Synchronous
User is waiting?
→ REST/gRPC via API Gateway
→ Add Circuit Breaker + Timeout
→ Cache responses where possible
High-throughput internal?
→ gRPC (binary, streaming)
→ Service Mesh for mTLS
Complex graph query?
→ GraphQL at BFF layer
→ DataLoader for N+1 prevention
NO → Asynchronous
Fan-out to many consumers?
→ Pub/Sub (Kafka topic)
→ Each consumer independent
Task queue / one consumer?
→ RabbitMQ / SQS queue
→ Competing consumers pattern
Distributed transaction?
→ Saga pattern (Choreography or Orchestration)
→ Compensating transactions for rollback
Need audit trail + replay?
→ Event Sourcing + Kafka
→ CQRS for read models

✅ Golden Rules
• Default to async — opt into sync when needed
• Design for failure — every call WILL fail eventually
• Make consumers idempotent — messages deliver at-least-once
• Always set timeouts — everywhere, no exceptions
• Propagate correlation IDs — through every call and message
• Use the Outbox pattern — never dual-write without it
• One database per service — no shared DB between services
• Version your events — schemas evolve over time
❌ Anti-Patterns
• Shared database between services (tight coupling)
• Synchronous chain of 5+ service calls (latency cascade)
• No circuit breakers (cascade failures)
• Unbounded retry loops (amplification storms)
• 2-Phase Commit across services (distributed lock hell)
• Fat event payloads with full objects (coupling + size)
• Ignoring message ordering requirements
• Service mesh from day one (premature complexity)
